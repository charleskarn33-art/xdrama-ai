# Module 2 — Auth & Multi-Tenant Core Schema

**Status:** Complete, pending your approval to move to Module 3.

## Architecture

Every table from this module onward is multi-tenant: a row belongs to an `organization`, and access is governed by the caller's `organization_members.role` (`owner` / `admin` / `member`). Two design decisions carry through the rest of the roadmap:

1. **State-changing operations that must be atomic or privilege-checked go through `SECURITY DEFINER` Postgres functions (RPCs), never raw client `INSERT`.** `create_organization` and `add_organization_member` are the only ways an organization or membership row comes into existence. This is what the Module 1 audit meant by "RLS on by default, deny-by-default" in practice — client `INSERT` privilege on `organizations`/`organization_members`/`audit_logs` was never granted at all, so the only door in is the function that also enforces the invariant (an org always has an owner; an actor must be owner/admin to add members).
2. **`public.is_org_member()` / `public.has_org_role()` are the reusable RBAC primitives.** Every future org-scoped table's RLS policies should call these two functions rather than re-deriving membership logic inline — that's the pattern Module 3 onward should follow.

## Database changes

New migration: `supabase/migrations/20260808184711_auth_core_schema.sql`.

- **`organization_role` enum**: `owner`, `admin`, `member`.
- **`profiles`**: one row per `auth.users`, created automatically by a trigger (`handle_new_user`) on signup. Holds `email`, `full_name`, `avatar_url`.
- **`organizations`**: `name`, `slug` (validated format, unique), `owner_id`.
- **`organization_members`**: composite PK `(org_id, user_id)`, `role`.
- **`audit_logs`**: append-only — no client `INSERT`/`UPDATE`/`DELETE` grant exists on this table at all; rows are written only by the RPCs and by a generic `audit_log_trigger()` attached to `organizations`/`organization_members` `UPDATE`/`DELETE`.
- **Guard**: `prevent_last_owner_removal()` trigger blocks demoting or deleting an organization's last owner.
- **RLS**: enabled on all four tables from creation. Supabase's current default (confirmed in `supabase/config.toml`'s `[api]` section, generated by this session's `supabase init`) no longer auto-exposes new tables to `anon`/`authenticated` — every grant in this migration is explicit, and `anon` gets nothing on any of these four tables.

### This was actually tested, not just reviewed

`supabase/tests/` stands up a throwaway local Postgres, fakes just enough of Supabase's platform (`auth.users`, `auth.uid()`, the `anon`/`authenticated`/`service_role` roles) to apply the real migrations unmodified, then runs `rls.test.sql` — 17 assertions that execute actual queries as simulated users, not a read-through of the SQL. It caught three real bugs before this ever reached the repo:

1. Missing `UPDATE` grant on `organizations` (RLS was correctly written, but the base privilege didn't exist, so even the owner got `permission denied` instead of the policy being evaluated).
2. `set_config(..., is_local => true)` inside the actor-switching test helper silently expired between psql's per-statement implicit transactions.
3. psql's `:'variable'` interpolation doesn't reach inside `do $$ ... $$` bodies, breaking cross-statement value passing in the test script itself.

Covered: profile self-service and cross-org profile visibility, org-creation atomicity, cross-tenant isolation (a non-member sees zero rows, not an error), role-gated updates (member blocked, owner/admin allowed), the last-owner guard (blocks demotion with one owner, allows it with two), audit-log visibility restricted to owner/admin, and `anon` having zero privileges. This now runs in CI (`.github/workflows/ci.yml`, `database` job) against a real `postgres:16-alpine` service container on every PR.

See `supabase/tests/README.md` for how to run it locally.

## Frontend

- **`/signup`, `/login`**: React Hook Form + Zod (`src/lib/validations/auth.ts`), calling server actions in `src/app/(auth)/actions.ts`. Validation is real — screenshotted with actual inline field errors, not asserted from reading the code.
- **`/auth/confirm`**: route handler for Supabase's email-link confirmation (`token_hash`/`type` PKCE flow), following the current `@supabase/ssr` (v0.12.4, the version actually installed) documented pattern.
- **`/dashboard`**: minimal — identity, organization list with role, a "create organization" form (wired to the `create_organization` RPC via `src/app/dashboard/actions.ts`), sign-out. Deliberately not the full app shell (nav, sidebar) — that's Module 3.
- **Route protection**: `src/lib/supabase/proxy.ts` now redirects unauthenticated requests to `/dashboard` → `/login?next=...`, and authenticated requests to `/login`/`/signup` → `/dashboard`. Verified live: `curl` against a running dev server returns a `307` to `/login?next=%2Fdashboard` for an unauthenticated `/dashboard` request, and no route 500s even when `NEXT_PUBLIC_SUPABASE_URL` points at a non-resolving placeholder host (the proxy's `auth.getUser()` call degrades to "no user" rather than crashing the request — worth confirming again once pointed at a real project, but the placeholder-host case is the one most likely to break a fresh clone).
- **Database types** (`src/lib/supabase/types.ts`): hand-written to exactly match the tested migration, in the standard `supabase gen types` shape (`Row`/`Insert`/`Update`/`Relationships` per table). `supabase gen types typescript` needs Docker even in `--db-url` mode (confirmed by actually running it against the local test DB — it fails on `docker.sock`), which isn't available in this sandbox. Regenerate for real once linked to a live project — the file says so in its header comment.

## Security

- RLS enabled on every new table from its `CREATE TABLE` statement, not retrofitted.
- No table grants `INSERT` to `authenticated` directly except `profiles` is not even insertable by clients — only the `handle_new_user` trigger (running as the table owner) creates profile rows.
- All `SECURITY DEFINER` functions use `set search_path = ''` (prevents search-path hijacking) and fully-qualified references.
- `EXECUTE` on every `SECURITY DEFINER` function is explicitly revoked from `PUBLIC` and re-granted only to `authenticated` — Postgres grants `EXECUTE` to `PUBLIC` by default on function creation, which would otherwise let `anon` invoke these (the functions do check `auth.uid() is null` internally, so this is defense in depth, not the only thing standing between `anon` and these functions, but it's the correct baseline regardless).
- Audit trail: every org/membership mutation is logged, and reading the log is restricted to owner/admin.

## Deployment instructions

No change to the deployment shape documented in Module 1. Two things worth doing once you have a live Supabase project:

1. In Supabase Dashboard → Authentication → Email templates / URL configuration, make sure the confirmation link points at `<your-app-url>/auth/confirm` (this project's route, not the Supabase-hosted default).
2. Decide whether email confirmation is required before sign-in (Supabase project setting) — the frontend works either way, but if it's required, a user who signs up won't be able to reach `/dashboard` until they click the email link, which is expected.

## What's deliberately not in Module 2

No OAuth providers (email/password only), no email-invite flow for adding org members (`add_organization_member` exists and is RBAC-checked, but there's no UI for it yet and no email delivery — that's a natural fit for a later "Team" surface, likely alongside the Admin Dashboard module), no organization switcher UI (a user with multiple orgs sees them all listed on `/dashboard`, but there's no "active org" context yet — Module 3's dashboard shell is where that belongs), and no custom JWT claims embedding org/role (would let the FastAPI orchestrator skip a DB round-trip for authorization checks, but there's nothing on the orchestrator side that needs org-aware authorization yet).
